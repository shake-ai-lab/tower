- 目的: 設計・実装・独立レビュー・利用者検証をつなぎ、結果を次の作業に反映する。
- 構成: 統括 + designer / implementer / reviewer / ideator / user_advocate / qa。

- 運用: 役割は必要時に起動。記録は統括がまとめ、重複編集を防ぐ。

## 2026-09-12: 初回適用「再起動後の自動再開」

- 日付・対象タスク: 2026-09-12。サーバー再起動で止まった作業中タスクを起動時に自動で続きから再開する（`manager.resumeInterrupted`、設定 `autoResume`）
- 編成: 統括が設計（設計書を scratchpad に 1 枚）→ implementer に実装を委任 → 差分を固定して reviewer と qa を並行 → 統括が指摘を判定して修正 → 単体テスト再実行。利用者役は使わなかった（画面の変更が設定のチェックボックス 1 個だけで、操作検証の価値が薄いと判断）。ideator も不要
- 観測された結果:
  - implementer: 設計書どおりに 8 ファイルを一発で実装、型検査・テスト通過。設計書から意図的にずらした点（定数化、存在確認）を自己申告してきたので判定が楽だった。所要 3 分強
  - reviewer: 中 2 件（指示のたびに余計な保存・配信が走り自動取り込みが二重に動く / 古い「中断」印を後から拾って一斉再開する）。どちらも設計書の見落としで、実装者の責任ではない。所要 3 分強
  - qa: 別データ置き場・別ポートで実サーバーを 7 回起動・強制終了し、受け入れ条件 2〜6 全部成功。受け入れ条件の外で 1 件（初回起動で `TOWER_PORT` が効かない既存バグ）を発見。所要 9 分強
  - 統括の手戻り: reviewer の 2 件 + qa の 1 件を統括が直接修正（15 行程度）。修正後に qa の再実走はせず、単体テスト（stale な印の除外）を足して代替
- 学び:
  - 設計書に「受け入れ条件」を観測できる形で書いておくと、qa がそのまま手順に落とせる。qa には「本物のデータとポートに触らない」環境の決まりを明記する必要があった（`TOWER_DATA_DIR` を今回追加）
  - reviewer と qa の並行は効く。qa が実サーバーを何度も起動し直している間はソースを触れないので、reviewer の指摘は qa 完了まで寝かせてからまとめて直す
  - 設計者と統括を兼ねると、設計の見落としを独立レビューでしか拾えない。今回はそれで十分だったが、契約（shared 型）を変える規模なら designer を分けて先に指摘をもらう価値がある
- 採否: 試行中（次の適用でも同じ流れが回るか見る）
- 独立レビュー: この記録自体は未レビュー
- 戻し方: AGENTS.md の流れを使わず統括が全部やる（従来どおり）

## 2026-09-12: 2 回目「使った量の台帳」「コマンドの日本語化」「探索のクリック」を並行

- 対象タスク: 3 件を同時に。A 使った量の台帳（消しても減らない）、B 英語の description を使わずコマンドから日本語を作る、C 画面操作の自由探索で Monaco 本文をクリックできない件の再現確認
- 編成: 統括が設計書を 3 枚 → implementer 3 人を並行（触ってよいファイルを重ならないよう分けた。C は「再現確認 → 必要なら修正」の実装者兼 QA）→ A・B の差分を固定して reviewer と qa を並行 → 統括が修正 → テスト追加
- 観測された結果:
  - 並行の 3 人はファイルが重ならず衝突なし。全員が「他の担当の差分は触っていない」と自己申告。所要は 3〜5 分ずつ
  - C は「今のコードでは再現しない」で終わった（旧方式では再現、現行方式で本文に文字が入ることを実測）。**再現確認を先に置いたので無駄な修正をしなかった**
  - reviewer: A に中 1（取り込みがトランザクションでない）・低 3、B に中 1（リダイレクト・xargs・find -exec を「見ています」と言う）・低 3。どれも設計書の見落とし
  - qa: 前回の QA が残した検証データとヘルパを再利用し、全シナリオ成功。統括が smoke 用に起動して止め損ねたサーバーがポート 4811 を塞いでいたのを見つけ、決まりどおり触らずに別ポートで続行した
  - 統括の手戻り: reviewer の 8 件のうち 7 件を直接修正、1 件（「全部」のタスク数の意味が変わる）は仕様として受け入れ。修正中に heredoc でバックスラッシュが潰れて型検査が落ち、Edit ツールで書き直した
- 学び:
  - 独立した小さな課題は implementer を並行させて良い。ただし「触ってよいファイル」を設計書で明示し、共有ファイル（shared 型・index.ts）は 1 人に寄せる
  - 「再現するか分からない」課題は、実装者ではなく「再現確認 → 証拠 → 必要なら最小修正」の依頼にする
  - 検証で起動したプロセスは統括も止め損ねる。QA に「自分が起動した PID 以外は触らない」と決めておいたので事故にならなかった。次回は smoke 用サーバーも同じヘルパで起動・停止する
  - 危険度に関わる文言（「見ています」）は、書き込み系のパターンを先に判定する設計にしておく。レビューで拾えたが設計段階で気づけた
- 採否: 試行中 → 2 回続けて回ったので、次回も問題なければ「採用」に上げる
